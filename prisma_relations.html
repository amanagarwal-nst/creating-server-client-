The problems

🔁 Rahul’s details repeat on every row.
✏️ One rename means editing many rows.
➕ Every new course copies Rahul again.
📅 No place for enrollment info like date or status.

✨ Better: each thing gets its own table, and tables point at each other using IDs. Now a rename changes one row. Those pointing IDs are called foreign keys.

Wait, why both studentId and student?

Think of a friend’s phone number versus actually calling them.

📇

studentId Int

The phone number written in your contacts. Just a number, like 1. It’s a real column stored in PostgreSQL.

📞

student Student

Calling that number to reach the whole person: name, email, everything. It’s a Prisma relation field. No column exists for it.

🧠 Remember: fields = the foreign key on this model. references = the field on the other model. For one-to-one, add @unique on the foreign key so two profiles can’t point at the same student.

      Why select instead of include?
      So the response has only what the frontend needs.
      
      
      Why go through enrollments to reach course?
      Student connects to Course through Enrollment. There’s no direct link.
      
      
      Where do the actual foreign keys live?
      On Enrollment: studentId and courseId.
      
      
      What if the student doesn’t exist, or has no courses?
      You get null for a missing student, and an empty enrollments array for no courses.

      🤫 Bonus: the lazy many-to-many
      
    
      We built Enrollment ourselves because we wanted extra info like status. If you need no extra info, Prisma can make the junction table for you:
      
    
      model Student {
  id      Int      @id @default(autoincrement())
  courses Course[]
}

model Course {
  id       Int       @id @default(autoincrement())
  students Student[]
}
// Prisma quietly creates a _CourseToStudent table
